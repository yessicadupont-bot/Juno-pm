## Problem & user

RocketShip PMs need this handled: Juno is a drafter, not a publisher. On a schedule it pulls metrics from Power BI, Roma and NPS, computes every delta with code, writes insights that describe patterns without claiming a cause, checks its own draft, and hands it to one human who approves.. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Juno will need to access the following systems for retrieving metrics needed to draft the dashboard and gain insghts: 
	Roma metrics for engagement (specified dashboard/query)
	Power BI metrics for adoption  (specified dashboard/query)
	NPS feedback for context and insights on engagement and adoption (specified query)
Confluence (specified link) for goals on new launches and KPIs for adoption and engagement 
Overall app metrics and amplitude metrics are excluded. These metrics are specific to PM area of ownership. So queries are refined to specific adoption and engagement metrics for area of ownership.

**How fresh must it be**

Metrics are pulled on a regular cadence weekly and monthly any changes that happen before or after the pull date do not get updated in the dashboard until the next pull date. 
If the source is unreachable, juno should not make up number it should retry two more times before escalating to PM to check the source as its unreachable.

## 02 Tools · System Capabilities

**The verb list**

Principle: the model reads metrics, code does arithmetic. Juno cannot put a number in the draft that did not come back from a tool result.
	Read changes nothing anywhere. 
	Draft changes only Juno’s own workspace and can be undone. 
	Write changes shared state. 
	Send leaves the product team. 
Juno has no write verb and no send verb: a write happens only when a human confirms a queued proposal, and a send happens only when a human publishes.
verbs:

	Read: pbi.get_series(report, tab, metric, n)

	Read: roma.get_funnel(widget, period)
	Read: roma.get_annotations(dashboard, since)

	REad: nps.get_scores(period, segment)

	read: nps.search_comments(period, score_range, keyword)

	context.get(doc)
	Read: Roadmap or strategy text with its stamped date

	Read: Metric definitions; launch names, dates, targets and bases

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

A scheduled run, not a chat. Weekly runs on Monday for the previous Monday to Sunday. Monthly runs on the 1st for the previous calendar month.
	1. Check freshness: every source has data through the period end.
	2. Pull metrics and series (batched per report tab).
	3. Compute deltas, flags, progress to target and streaks with the calc verbs.
	4. Pull NPS and Roma detail only for specified items (adoption, engagement, feedback).
	5. Draft insights and At a glance.
	6. Hand to the verifier, fix and re-verify once.
	7. Save the draft and notify the reviewer.
Turn ceiling (starting values, tune after two runs). Hitting any limit stops the run, ships a partial draft marked incomplete, and names the limit that was hit. It never loops on.

**Latency and cost target**

for fetching metrics it should not wait longer then 1 minute to retreive any single metric from the queries. 
since these are simple tasks model should answer back in less then 1 minute per task, however anything longer then 10 minutes should stop so as to not exasberate cost and should notify PM that it was a longer then normal run to check why.

## 04 Memory · Data Requirements

**What persists, at what scope**

Juno retrieves current and historical metrics from the source system to generate comparisons. Metrics may be cached temporarily to support dashboard performance, with freshness clearly displayed. Juno retains generated insights for 180 days, including the analysis date, reporting periods, and source references. Historical metric snapshots are retained only where required to reproduce a saved analysis.
Juno stores insights and analysis derived from collected metrics for a rolling 180 days and makes them available to authorized members of the team that owns the dashboard. Insights older than 180 days are automatically deleted. Confidential information, such as customer names, must be excluded from shared dashboard content. Dashboard data must not be accessible to users outside the authorized team.
Juno remembers users preferences for seeing metrics for US market. 
Juno stores the changes made and by whom for tracking and the team can see these as well.

**Expiry and write rules**

Corrections from the dashboard owner or an authorized reviewer take precedence over Juno’s generated analysis. Juno records who made each correction and when, and uses the corrected explanation in future responses about that analysis. Conflicting corrections are flagged for the dashboard owner to resolve.
correcting an explanation should not silently change the underlying metrics. If someone disputes a number, Juno should verify it against the source system

## 06 Verification · AI Testing & Measurement

**The check before output ships**

Before Juno publishes a dashboard or update, it runs a separate verification pass using fresh context. The verifier receives the draft output, supporting tool results, source references, and metric dictionary. It does not receive the drafting model’s internal reasoning.

Deterministic checks run in code. Checks requiring interpretation also use a separate model pass. Each check returns Pass, Warn, or Fail, with an explanation and a reference to the affected content.
| ID | Check | Acceptance criteria | Verification method | On failure |
|---|---|---|---|---|
| **V1** | Numeric traceability | Every reported metric value is traceable to a supporting tool result and a source link. | Code | Block publication |
| **V2** | Calculation and rounding | Deltas, percentages, and progress toward targets are recomputed from unrounded source values. Results are displayed to one decimal place using round-half-up. | Code | Block publication |
| **V3** | Period and metric alignment | Reporting and comparison periods match the reporting cadence. Each metric uses the same definition, units, and calculation basis as its target. | Code | Block publication |
| **V4** | Source freshness and completeness | Source data covers the required reporting period through its end date. Any permitted partial period is explicitly labeled and flagged. | Code | Block publication |
| **V5** | Unsupported causation | Outside quotations, the output contains no explicit causal language, including “because,” “due to,” “driven by,” or “led to.” It also contains no implied causal claims. | Code + model | Block publication |
| **V6** | Launch and roadmap accuracy | Launch and roadmap claims match the approved registry and preserve the roadmap’s wording and qualifications. Tier C documents may be cited only if stamped in the current quarter. | Code + model | Block publication |
| **V7** | Confidentiality | Output contains no customer names, ARR figures, individual names, or ticket text. | Code | Block publication |
| **V8** | NPS rules | NPS uses the fixed 10,000-response sample. Any other sample size creates a clarification item. A change of 0–2 points is labeled “minor”; a change greater than 2 points is flagged. | Code | Block publication |
| **V9** | “Flat” classification | A change is classified as “flat” when its displayed, one-decimal value falls within −1.0% to +1.0%, inclusive. Changes outside this range receive a flagged badge and matching wording. | Code | Warn |
| **V10** | Repeated insights | Insights from the previous update are not repeated unless the associated streak has changed. | Code | Warn |
| **V11** | Unresolved clarifications | Open clarifications from the previous run are carried forward and attached to the affected metrics. | Code | Warn |
| **V12** | Output structure and citations | The output contains exactly three “At a glance” bullets, and every insight includes a supporting source reference. | Code | Warn |
Handling verification results
- Pass: The content meets the acceptance criteria.
- Warn: Publication may proceed, but the unresolved issue must be visible alongside the affected content.
- Fail: Publication is blocked until the issue is corrected and the revised output passes verification.
If a blocking check cannot be completed—for example, because required evidence is unavailable—Juno must treat it as a failure. It must explain the issue and the next step rather than silently discard the output. Any correction to the draft must be verified again before publication.

**Failure behaviour**

When a validation check fails, Juno must identify the affected content, explain the issue in plain language, and provide a next step where available. Verified dashboard sections remain visible. Missing or unverified data must not be presented as confirmed findings or substituted with zero. Any permitted use of previously retrieved data must clearly display its timestamp and refresh status.
